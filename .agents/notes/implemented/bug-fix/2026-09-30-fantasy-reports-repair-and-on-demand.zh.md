# Agent Note: Fantasy 报告的修复键、触发可见性与按需报告

Status: implemented

[English](2026-09-30-fantasy-reports-repair-and-on-demand.md) | 中文

## 问题

2026-09-30，Googies 完整报告在下午 6:00 触发三分钟后被扣留：事实修复阶段返回 `{"players":[{"id":"P14","recommendation":"START",...}]}`，补丁解析器以 `players[0].player must be a string` 拒绝了它。两份修复提示都要求行“complete with the same schema and id”，这会诱使模型使用 `id` 键，而草稿行以 `player` 为键。

同一天 90 分钟后定时的 Lights 完整报告没有留下研究运行、阶段 Session 或失败通知。触发结果以 info 级别记录，而部署的日志导出器会丢弃 info，因此被跳过的触发不可见。插件 effect 被释放时仍在排队或运行的触发不会留下任何日志，因为释放开始后队列吞掉所有错误；此时仍在排队的触发还会对正在停止的插件调用 Yahoo，然后静默失败。失败之后也无法重跑某支球队的报告：定时触发会跳过已有运行的比赛周与模式。

## 决策

两份修复提示现在都点明键名并给出示例行 `{"player":"P14","recommendation":"START",...}`，提示版本改为 `fantasy-weekly-v3`。补丁解析器只在补丁行中接受 `id` 作为 `player` 的别名；已有 `player` 的行保留该值，撰写阶段的草稿仍必须使用 `player`，因此别名无法掩盖未写球员的草稿。阵容行仍须使用 `player`，因为修复提示以 `player` 键展示当前阵容。

除 `published` 和 `redelivered` 外，每个触发结果现在都以 warn 级别连同原因记录。被释放放弃的触发以 warn 级别记录 `abandoned because the plugin stopped`，排队中的触发在开始任何工作之前先检查释放信号。

人类命令 `/fantasy-report <team> [full|thursday|sunday]` 把一次触发方式标为 `manual` 的报告运行加入队列，针对包含今天日期的 Yahoo 比赛周，并立即回复。只有 `commandPresets` 至少列出一个 Agent 预设时才注册该命令；处理器只接受记录的预设在列表中的 Session；球队可选的 `commandPresets` 进一步限定谁能请求该球队，足以让某位球队主人的通道只能请求她自己的球队。手动运行忽略同一比赛周与模式的早先运行，定时与补跑的时段检查也忽略手动运行，因此重跑既不会压制也不会重复该时段的定时报告。日期超出报告周时以通知失败而不是跳过，因为请求者已被告知运行已开始。手动运行与触发共用队列，因此不会有两份报告重叠，但它既不等待也不重置 `minimumStartGapMs`，因为等待重跑的人不应再等最多 90 分钟。

## Lights 调查

一个测试在 fake timers 下用真实的 croner 定时器挂载两支完整报告相隔 90 分钟的球队，使用默认的 `minimumStartGapMs` 5,400,000，并让第一支球队的运行被扣留：第二次触发按时开始运行并发布。croner 的重叠保护无法丢弃触发，因为定时器回调只是入队后返回。启动间隔从第一次运行开始时计算，它比第二次触发早不到 90 分钟，因此等待最多几秒。失败的第一次触发通过其通知正常返回，因此队列没有被阻塞。

其余不留下运行也不发送通知的路径是 `skipped` 结果（比赛周超出 `firstWeek` 到 `lastWeek`，或同一比赛周与模式已有早先运行），以及插件 effect 被释放，例如某个注入的服务被移除或重新加载之后。两者在部署日志中都不可见；现在都以 warn 级别记录。现有证据不足以确定线上的根本原因。

## 考虑过的替代方案

- **在每个行解析器中接受 `id`** — 否决，因为省略 `player` 的撰写草稿是修复循环应当看到的结构错误，而撰写提示从未提到 `id`。
- **让手动请求绕过队列** — 否决，因为两个并发的报告运行会争用唯一的模型服务器，并破坏时间表所依赖的逐个执行保证。
- **像定时运行一样为手动运行设置间隔** — 否决，因为回复承诺会尽快运行；共用队列已防止重叠。
- **在定时时段检查中计入手动运行** — 否决，因为失败或提前的手动运行会因此静默压制定时报告。

## 影响

以 `id` 为键的修复补丁会被应用，而不是扣留报告。只保留警告的部署能看到每次被跳过、扣留、失败、未投递和被放弃的触发。配置过的用户可以在 Discord 中重跑某支球队的报告，结果或失败通知投递到定时报告的去处，包括影子频道。`/fantasy-report` 总是报告当前比赛周。
