# Agent 笔记：通过用户作用域、审批门控与轮次提醒实现 skill 自我改进

Status: implemented

[English](2026-09-05-skill-nudge-and-user-scope.md) | 中文

## 问题

`skill_manage` 只能写入当前工作区的 `.agents/skills`，因此在一个仓库里跑通的操作流程在其他任何地方都不可见，而持久的个人流程根本没有容身之处。模型也缺少沉淀压力：发明了一套多步调用流程之后就戛然而止，因为从来没有任何机制问过它这套流程是否可复用。与此同时，每次变更都无条件落盘——有人盯着时尚可接受，但在应当把写入交给审阅的通道里并不可接受。

## 决策

`skill_manage` 新增了 `scope` 参数。默认的 `workspace` 作用域保持不变；`user` 在 `resolveDshHome()/skills` 下写入扁平文件——文件系统 skill 提供方已把该根目录作为其 `user-dsh` 来源扫描，因此无需改动提供方配置，用户作用域的 skill 在每个会话中都会加载。`enableUserSkillManagement`（默认 false）按调用把关该作用域；被禁用的请求会以模型可见的消息拒绝。`requireApproval`（默认 false）在调用时把创建、更新和删除路由给审批服务，沿用 memory 工具的模式：未挂载应答者即拒绝而不是回退，只有 `allowed-once` 才继续。

技能编写权归属于派发工作的顶层 Session，因为子 agent 经常执行调用方编写的只读任务。持久的子会话来源在恢复后也将其排除。提醒的 Session 范围时机和生命周期由[Session 范围的技能提醒与草稿检查](2026-09-27-skill-nudge-quality.zh.md)记录。启用管理功能或提醒后，两个目录模板都会告诉模型：若已加载技能的结果中含有压缩裁剪标记 `[... tool result middle pruned ...]`，其步骤不完整，必须先按名称重新加载再照做。

## 备选方案

仅靠提示词要求“保存重复流程”的方案被拒绝，因为它会在模型完成任务时与任务本身争夺注意力；轮次后的提醒会在工作完成后出现。进程内计数后来被[Session 投影决策](2026-09-27-skill-nudge-quality.zh.md)取代，该决策负责已完成轮次和恢复后的要求。

把用户作用域文件写到 `~/.agents/skills` 被否决，改选 `$DSH_HOME/skills`：该根目录已是带显示路径支持的既扫描来源，而 home 层的 `.agents/skills` 需要改动提供方，且在概念上与各工作区根目录相冲突。

在注册表或文件系统层做审批被否决：被执行的决策是“这个 agent 的这次变更”，它属于做出该决策的工具；审批服务可能合理地缺席，那是拒绝理由而非注入依赖。

## 后果

Beardy Web 和 Discord 预设开放用户作用域，并把提醒阈值设为 20 次调用；技能写入需要审批，无人值守通道仍关闭提醒。`skill-nudge` 来源类型加入 `MessageSourceMap`，每条提醒都可从 Session 日志重建，并在可复用的请求前缀之后新增一条留存消息。

审批门控的 skill 写入在没有应答者的通道里会被拒绝，与 memory 的立场一致：暂存存在的意义是由人来答复，无人应答的队列不是写入的许可。用户作用域的 skill 是全局权威——一份糟糕的已保存流程如今会跟随每个会话——这正是该作用域需要独立配置开关、而不是搭 `enableSkillManagement` 便车的原因。
