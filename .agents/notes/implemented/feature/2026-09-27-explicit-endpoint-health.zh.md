# Agent Note: 显式端点健康与状态转换通知

Status: implemented

[English](2026-09-27-explicit-endpoint-health.md) | 中文

## 问题

无人值守的模型端点可能连续数天不可达，定时运行持续失败，却没人收到明确的 provider 告警。仅有对话状态不能展示端点可达性；再发布一条 cron 失败通知又会重复网关现有的结果投递。

## 决策

`dsh-health` 只轮询显式配置的 HTTP 端点。每个探测有唯一名称、URL、可选凭据引用和期望状态码。连续失败和恢复阈值改变进程内状态；初始健康观察不发通知。宕机和恢复转换以在接收重试期间保持稳定的标识进入 Discord 网关的持久 outbox。接收失败期间端点探测仍会继续，待处理的转换在接收恢复后按顺序提交。按通知类型分别计算的冷却期限制状态反复波动时的重复通知，但不隐藏首次恢复。Host 通过网关 `/status` 展示当前状态。

Cron 的持久任务历史向 Discord 和 Web 命令输入中的 `/cron status [name]` 提供结果、运行时长、失败原因和下次触发时间。网关在现有的唯一失败运行结果通知中加入任务名、Session id、代码和下次触发时间；不会另发 cron 健康告警。health 插件在网关投递前观测 cron 结果，并仅向 `/status` 暴露最近一次失败事实的只读快照。

## 曾考虑的替代方案

**探测猜测的通用 models URL。** Provider 的端点、认证和状态语义各不相同；猜测的 URL 会给出误导性的健康结论。部署配置逐一指定目标。

**保存事故或重启 provider。** Host 无法从 HTTP 结果推断安全的恢复操作。调度器与网关已分别拥有持久运行历史和投递；另一套事故存储会重复这些职责。

**由 health 发布 cron 失败。** 网关已将 cron 结果接收到 outbox。第二个监听器会向用户发送重复消息，并使确认责任不清。

## 后果

操作者收到按阈值判定的宕机和恢复通知，并可在不开启模型轮次的情况下查看当前状态。HTTP 成功只证明端点可达，不证明生成质量。探针状态和网关最近一次 cron 失败在重启后重置；持久 cron 历史及已接收的 outbox 条目仍由现有所有者保留。
