# Agent Note: 摄像头画面随过期的历史记录一起删除

Status: implemented

[English](2026-09-27-camera-frame-retention.md) | 中文

## 问题

[摄像头监视](2026-09-27-ring-camera-events.zh.md)为每个事件在附件存储中保存最多三张 JPEG 画面，并为每个事件打开一个分类 Session。`retentionDays` 只清理历史记录，因此一个对着车道的摄像头每天会让存储无限增长数十兆字节。Goran 希望摄像头占用的存储有上限。

## 决策

附件服务定义新增 `deleteImage(ref)`：它删除一张规范化图片以及由它派生的所有请求版本，并报告对象是否由本次调用删除。存储不统计引用，因此约定把所有权交给调用方：调用方必须拥有该引用的全部持有方，并跳过仍被保留的持有方引用的图片。基类以 `ATTACHMENT_DELETE_UNSUPPORTED` 拒绝，因此其他提供方和测试替身的行为保持不变。本地提供方校验 `sha256:` id；对象解析后的路径不是解析后根目录内的预期路径时拒绝删除；然后清除只读属性、删除对象、同步其分片目录，并移除该附件的请求版本目录。请求版本按附件摘要命名的目录分组，因此删除无需索引即可找到它们；变体身份保持不变。

监视插件的保留清理在启动时运行，此后每次在上一次清理结束 `sweepIntervalMs` 后再次运行；间隔上限为一天。对每条因时间或条数过期的记录，清理先删除既不被保留记录引用、也不被未完成事件引用的画面，再删除记录。画面删除失败时保留其记录，由下一次清理重试；已经不存在的画面视为已删除，因此重复清理是幂等的。删除了内容的清理会以 info 级别记录事件数和画面数。Discord 发件箱在发送时读取画面，画面不可读时本来就只发送文本。

分类 Session 留在会话日志中。`SessionPersistence` 提供 `create`、`open`、`flush`、`stat` 和 `list`，其 README 把删除归为带外的后端维护。监视插件不会绕过持久化层删除任何会话文件。

## Session 保留还缺少什么

删除分类 Session 需要会话持久化提供受支持的途径，而目前没有：

- 一个操作，例如 `SessionPersistence.delete(id)`：拒绝存在活跃写入所有者的 Session（进程内占用以及 JSONL 的内核租约），在读取方无法观察到中间状态的一步中移除该 Session 的全部存储产物，并规定之后 `stat`、`list` 和 `open` 的返回结果；
- 移除或失效以 Session id 为键的状态，例如工作区注册表的头部索引及其归档和置顶集合、会话投影缓存，以及通过 `api-session/removed` 通知的在线 Web 客户端；
- 针对引用已删除 Session 的记录的规则，例如父 Session 目录中的子代理子 Session。

工作区归档只会在分组视图中隐藏 Session，不会释放存储，因此监视插件不把它用作保留手段。

## 考虑过的替代方案

**由监视插件删除分类 Session 文件。** 这会绕过写入租约，使进程内 `stat` 和 `list` 的结果以及派生索引过时，并让消费方依赖某一个后端的文件布局。

**在附件存储中做引用感知的垃圾回收。** 要证明对象未被引用，就必须扫描每个 Session 日志，包括 fork 和恢复的 Session，而附件 seam 推迟了这一设计。由所有者删除无需扫描，因为监视插件拥有其画面的全部持有方。

**保留每张画面直到其分类 Session 被删除。** Session 没有删除操作，因此画面永远不会被删除。

**接收 `AttachmentId` 而不是图片引用。** `readImage` 和 `imageHostPath` 都接收图片引用，而且引用类型让图片命名空间与原样文件分开。

**为每个附件的缓存请求版本建立索引。** 索引是更多需要保持一致的持久状态；按附件摘要对缓存分组无需额外写入即可提供同样的查找。

## 后果

画面和历史记录受 `retentionDays` 与 `maxHistory` 约束。在会话持久化提供删除之前，分类 Session 日志仍会为每个已分类事件增加一份小日志。保留清理删除画面后，读取分类 Session 的图像会以 `ATTACHMENT_NOT_FOUND` 失败，因此其模型输入只在保留期内可从日志重建。仍在 Discord 发件箱中等待的通知只发送文本。

监视插件拥有其记录的每个事件的画面；在保留期之后仍保留画面引用的其他 `camera/event` 监听器会发现画面缺失。清理只通过历史记录找到画面，因此记录已不存在的画面会保留其对象；关机时从队列中丢弃的事件、与已记录事件 ID 重复的事件，以及指向未知设备的事件，也都会保留其画面。清理也看不到提供方为尚未发布的事件保存的画面；当这样的画面与某张过期画面字节相同时，共享对象会被删除，该事件的分类会读到画面缺失。按附件摘要分组之前缓存的请求版本会保留到缓存目录被清空为止，清空缓存始终是安全的。

附件测试固定了以下行为：对象及其请求版本的删除、对象不存在、无效 id、拒绝经由指向存储之外的链接到达的对象、删除失败，以及与删除竞争的读取。监视插件测试固定了精确的时间边界、按条数清理、与保留记录或未完成事件共享的画面、失败重试、已删除的画面、启动时补清理，以及清理过程中的销毁。一个 Discord 网关测试在保留清理于发件箱接收之后、发送之前删除画面时，只发送文本。
