# Agent Note: Discord 轮次进度通知

Status: implemented

[English](2026-09-29-discord-turn-progress-notice.md) | 中文

## 问题

2026-09-29，一个研究类 Discord 请求在本地模型上以中等思考强度运行了五个工具步骤。达到 600000 ms 的 `turnTimeoutMs` 后，网关释放了对话、丢弃了回答，并发送了超时通知。部署已将 `turnTimeoutMs` 提高到 1800000，但在长轮次期间频道只显示正在输入提示和 👀 表情，用户无法区分轮次是慢还是卡住。

## 决策

`@deepseek-ai/dsh-discord-gateway` 新增经过校验的 `turnProgressNoticeMs` 字段，默认 180000。`0` 表示关闭通知，`assertConfig` 拒绝其他任何不短于 `turnTimeoutMs` 的值。`runTurn` 在把消息交给 Agent 之后，通过路由器的 `wait` 接缝设置一个计时器。计时器先触发时，路由器通过现有的 `notice` 路径发送 `TURN_PROGRESS_NOTICE`，因此它进入持久发件箱，并在 `richMessages` 下渲染为带对话控件的卡片。通知发到该轮次自己的频道，因此用户专属通道的通知会发到该用户的私信。

计时器信号组合了路由器的关闭信号、`/stop` 与 `/new` 会中止的频道输入信号，以及每轮一个的控制器。轮次结束或超时时，`runTurn` 在 `finally` 块中中止该控制器；`releaseConversation` 与 `dispose` 通过 `LiveConversation.cancelProgress` 中止它。回调会再次检查组合信号，因此在取消之后才返回的延迟接缝不会发送任何内容。通知不改变轮次，也不改变 Session 日志。

轮次期间到达的消息保持现有的串行行为：它们排在频道尾链上，只在 `runTurn` 返回后运行，因此在各自轮次开始时设置自己的通知，从不共享或重新设置正在运行轮次的计时器。通知回调只通过 `track` 排入一次发送；它从不触碰尾链或轮次状态。

## 考虑过的替代方案

**按间隔重复发送通知。** 一条通知已能回答“是否仍在运行”；正在输入提示本身已在重复，重复发帖只会增加频道噪音。

**让通知文本可配置。** 网关的其他通知都是固定文本；该文本不包含任何部署细节，配置字段只会增加表面积。

**为预设命令和主动轮次设置计时器。** 所报告的等待来自入站消息；预设命令轮次与主动轮次保持现有呈现方式。

## 后果

等待审批或提问回答的轮次在超过阈值后仍可能发送通知。通知对模型不可见，也不写入 Session 日志，因此没有快照变化。测试使用 Vitest 假计时器覆盖阈值、提前结束、关闭、串行消息、超时、`/new`、释放路由器与专属通道路径，并用手动延迟接缝覆盖延迟返回。
