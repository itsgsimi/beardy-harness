# Agent Note: 持久化个人 agent 投递与中断运行恢复

Status: implemented

[English](2026-09-07-durable-personal-agent-delivery.md) | 中文

## 问题

个人 agent 完成的回答可能比网络连接存续更久，提醒也可能比已挂载的 Agent 存续更久。把传输失败当作最终投递结果会丢失有用的工作。保留每个已挂载的对话可以避免一种提醒失败，却会消耗资源，而且仍无法跨进程重启存续。定时运行还需要区分等待投递的已完成回答和不能安全重复执行的中断操作。

## 决策

Discord 网关拥有一个有界持久发件箱。它在发帖前持久保存完整文本或已格式化的消息体，对已确认的分块设置检查点，并在配置的去重窗口内保留已完成投递的标识。传输重试继续发送排队消息，不会重新运行 agent。富消息体与临时交互响应遵循[展示决策](2026-09-07-discord-native-interactions-and-presentation.zh.md)。对话记录为已接受的最终回复设置检查点，因此启动时可以恢复尚未进入发件箱的已提交输出。队列容量、内容大小、回执保留量和重试延迟均由部署配置。

网关还只检查其已登记 Discord 会话中的待执行调度。最早的提醒到期时，它恢复所属会话，并将派发交给该会话现有的 Schedule 插件。活动 Agent 会取消冷会话计时器并阻止空闲释放；`/stop` 会取消入站消息轮次与主动轮次。这保留了[持久调度](2026-08-05-durable-web-schedule.zh.md)的 agent 作用域归属。

Cron 在打开 Session 前记录运行预约。结算先一起记录终态结果和待投递内容，再交给渠道监听器。监听器只在持久接受后确认；未确认结果会重试，但不执行模型。启动时将剩余预约标记为中断并报告，不会重新执行其操作。主机停止期间错过的表达式触发时间会跳过；调度器安排下一个未来触发时间。每次触发都会读取当前的连续性笔记。

此决策替代[主机 cron 与 Discord 投递](2026-09-05-host-cron-with-discord-delivery.zh.md)及[运行时管理 cron](2026-09-05-runtime-managed-cron-jobs.zh.md)中自动结果投递的尽力而为策略。直接 `discord_send` 工具调用保留自身的立即发送语义。[持久对话路由](2026-09-05-discord-durable-conversations.zh.md)仍负责渠道标识与恢复选择。

## 考虑过的替代方案

**发帖失败后重新运行 agent。** 已完成的运行可能已经改变外部状态。持久保存回答可避免重复操作并避免再次支付模型运行费用。

**保留所有已挂载的对话 Agent。** 这能保留活动计时器，但会无限期消耗资源且无法覆盖重启。网关可以只恢复自己拥有的会话，而无需把核心调度器变成全局会话扫描器。

**承诺 Discord 精确一次投递。** 进程可能在 Discord 接受 POST 后、本地检查点落盘前停止。本地事务无法让远程操作成为原子操作；分块检查点和有界回执减少重复，但不会隐藏这种不确定性。

## 后果

在远程 POST 与本地检查点之间的崩溃窗口内，投递语义为至少一次。队列耗尽时拒绝持久接受，而不是丢弃较早的待投递内容。存在待投递输出的 cron 任务会等待接受后才开始下一次运行。关闭会取消计时器和运行中的工作，并等待持久化与投递操作结算后再关闭存储。这些保证要求每个 bot token 仅运行一个进程，且仅覆盖配置的 Discord 目的地；它们不提供 Google 账号集成或自动技能评估。
