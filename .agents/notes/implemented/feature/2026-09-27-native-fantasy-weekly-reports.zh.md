# Agent Note: 以研究工作流实现原生每周 Fantasy 报告

Status: implemented

[English](2026-09-27-native-fantasy-weekly-reports.md) | 中文

## 问题

Beardy 为家中两支球队生成的每周 Fantasy 报告原先运行在外部 Python 服务中：它读取手工录入的阵容，通过远程 API 启动研究，再借助文件把渲染好的文本交回 Discord 网关。阵容与 Yahoo 逐渐不一致，报告的模型调用和证据保存在 Harness 日志之外，而服务的防护措施（以阵容为先的来源、姓名采纳、原文引用、阵容检查、有锚定的审阅、有界修复、发布把关）只存在于那个服务中。Harness 现在可以直接读取 Yahoo 并执行持久研究，因此这些报告需要一条保留上述防护、并记录每次模型调用的原生路径。

## 决策

`dsh-fantasy-reports` 为每支配置的球队安排三份报告，并把每份报告作为 `ctx.research` 的使用方工作流运行。研究服务定义新增 `ResearchWorkflow`：使用方向 `start` 传入一个有名称、有版本的流程，提供方在 `research/started` 中记录名称、提示词版本和时限，用有日志、无工具的阶段以及与通用引擎相同的账本写入执行该流程，并把返回的报告提交为完成结果。研究相关的包保持与领域无关；Fantasy 流程及其上限和提示词属于 Fantasy 使用方。

Yahoo 是阵容、合格位置、当前阵容位、状态、轮空周、联盟阵容位、计分、对阵和预测分数的权威来源。网页只有写出其所针对的球员时才被采纳；任何模型读取页面之前，反向的赛程强度序数会被改写，FantasyPros 排名标题会被移除。代码检查每份草稿：引文必须来自写出该球员的页面原文，阵容必须完整覆盖，首发阵容必须用既未轮空、也未被标为不可出场的合格球员填满联盟的 Yahoo 首发位。结构性失败得到有界修复补丁，不消耗事实审阅次数。审阅发现只有逐字引用草稿及所引证据时才计入；最后一次审阅后若仍有错误球队、赛程或赛季的发现，报告被扣留，其他发现再修复一次并在报告中注明。已接受的草稿由代码渲染，因此不会有模型改写已通过的建议。

投递使用调度器的 `cron/run-finished` 交接进入 Discord 网关的持久发件箱。被扣留或失败的报告会发送不认可任何建议的失败通知。运行使用 profile 范围的研究所有权，每支球队使用一个稳定的调用方 Session，因此早先完成的报告会成为对比上下文，并可通过 `deep_research` 读取。影子模式在与旧服务并行的切换周内，把所有报告和通知发送到一个配置的频道，并附上球队标签。

## 考虑过的替代方案

- **把 Fantasy 引擎放进本地研究提供方** — 否决，因为通用提供方会依赖 Fantasy 服务并携带 Fantasy 配置，研究定义也会导入 Fantasy 类型。
- **把报告作为普通 cron Agent 轮次，并使用 Fantasy 与网页工具运行** — 否决，因为开放式工具循环无法在投递前强制执行以阵容为先的覆盖、原文引用、阵容合法性或审阅关口。
- **保留外部服务，只从 Yahoo 同步其阵容** — 否决，因为其模型调用、来源和审阅仍在 Harness 日志之外，其防护措施也仍在 Harness 之外重复存在。
- **从单独的 NFL 赛程数据源解析对手和开球时间** — 暂缓；Yahoo 的轮空周和状态已能让代码拒绝没有比赛的首发，对手相关陈述仍由审阅依据被引用页面核对。

## 后果

每份报告都是普通的研究运行，其阶段、来源、采纳决定、草稿和审阅都能从其 Session 与证据文件重建，Beardy 可以按 ID 重新打开任何报告。研究定义为其他需要固定覆盖和把关的流程提供了稳定的扩展点。每次运行比通用引擎消耗更多模型调用，但受审阅与修复上限约束。因重启中断的运行不会在其时段内重试，投递交接持续失败的报告只保留在研究历史中。对手和开球时间仍来自来源，而不是由代码核对。
