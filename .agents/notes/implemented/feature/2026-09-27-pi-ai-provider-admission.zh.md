# Agent Note: pi-ai 提供方路由的进程内准入

Status: implemented

[English](2026-09-27-pi-ai-provider-admission.md) | 中文

## 问题

多个进程内 subagent 会话可以同时请求同一个单槽位本地模型。服务器对超额工作排队，而 harness 会把每次未完成的流读取视为提供方空闲时间。排队请求因此可能在服务器开始响应前耗尽 `streamIdleTimeoutMs`，随后触发重试并加重队列。

## 决策

`llm-pi-ai` 为每个提供方 profile 提供可选的正安全整数 `maxConcurrentRequests`。省略时保持不限量分派。设置上限后，一个适配器实例内同一路由的请求按先进先出顺序准入。`queueTimeoutMs` 是另一个可选的正有限排队期限，受 Node 计时器范围限制，并要求设置并发上限。省略时，等待者会一直排队直到准入或中止。排队期间中止会移除等待者；已准入的流在成功、终止错误、调用方中止、空闲超时或消费者结束时才释放槽位。流空闲看门狗在准入后才创建，因此排队时间不消耗其预算。

准入计数由适配器实例和提供方路由拥有，独立于不可变配置快照。设置变化后，活跃调用仍被计数；排队调用保留其捕获的上限和期限。进程内 `spawn` 子智能体共享父级 LLM 服务，因此受到同一限制。独立进程不共享该计数。

排队期限到期会抛出带 `ADMISSION_TIMEOUT` 的 `LlmError`，与提供方 `TIMEOUT` 区分。该代码不在默认可重试集合中：向已满的本地队列重试会增加需求，却不会释放槽位。提供方可以在 `retryPolicy.retryableCodes` 中显式加入它。准入等待不单独记录日志；终止错误沿用现有请求失败路径。

## 考虑过的替代方案

**把队列放进 `dsh-llm`。** 提供方无关的服务不拥有部署上限或 pi-ai 分派点。在那里加入提供方专属准入，会把策略强加给其他适配器，却无法协调各自不同的传输。

**提高 `streamIdleTimeoutMs` 或服务器并行度。** 更长的空闲预算会把服务器排队时间藏在传输超时中。更多服务器槽位会占用模型上下文或内存。两者都不能提供带调用方取消功能的有界客户端队列。

**默认重试准入超时。** 超时尝试尚未到达提供方，但自动重试会重新进入同一个饱和队列。容量会变化的部署仍可使用显式的逐路由重试策略。

## 后果

一个适配器实例现在为每条路由持有请求队列和活跃计数器。排队超时与中止会先移除监听器和计时器，再考虑下一个等待者。槽位在流清理后才释放，因此消费者提前结束时，不会在其 SDK 流仍在关闭期间放行下一个请求。共享服务器的独立进程需要各自设置上限，或使用外部协调器。单元测试覆盖先进先出顺序、设置校验、排队取消与超时、所有流退出路径，以及超过空闲间隔的排队等待。
