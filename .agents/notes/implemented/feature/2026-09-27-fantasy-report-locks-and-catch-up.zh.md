# Agent Note: Fantasy 报告的阵容位锁定与重启补跑

Status: implemented

[English](2026-09-27-fantasy-report-locks-and-catch-up.md) | 中文

## 问题

每周 Fantasy 报告在推荐阵容时并不知道 Yahoo 已锁定了哪些球员。周日时，周四晚场的首发不能离开其阵容位，比赛已结束的替补也不能首发，但经代码检查的阵容仍接受这两种调整。在 Harness 重启期间触发的时段，或运行被重启中断的报告，都不会重试；投递交接失败的已完成报告也只保留在研究历史中。

## 决策

Yahoo 阵容行带有 `is_editable`；`0` 表示该球员本周的阵容位已不能更改。`fantasy` 能力将其公开为可选的 `FantasyPlayer.slotLocked`，Yahoo 提供方只在响应带有可识别的标志时设置它，因此联盟球员分页和无法识别的值不做标记。`fantasy` 工具随阵容序列化该字段，其描述说明锁定阵容位的含义。报告撰写阶段对每个阵容行都能看到 `yahooSlotLocked`；阵容代码检查要求被锁定的首发保留其当前 Yahoo 阵容位，并禁止被锁定的替补首发；渲染出的报告在阵容旁列出每名被锁定的球员，并标记每个被锁定的行。被锁定的首发免于可出场检查，因为即使 Yahoo 随后将其列为缺阵，也无法再移动他。

插件启动时，若每支球队在该时刻或之前的最近时段触发距今不足 `catchUpWindowMs`（默认 12 小时；`0` 关闭补跑），就对其复查一次。周日时段取该窗口与 `sundayCatchUpWindowMs`（默认 2 小时）中较短者，从该球队自己的周日时段起算，并在启动间隔等待结束后再次检查窗口，因此补跑的周日报告不会在截止后开始。之所以按模式采用相对窗口而非绝对的开球时刻，是因为每支球队的周日时段本已相对开球时间设定，这样同一套时段运算即可用于所有模式。时段时间来自 `dsh-cron` 的 `latestMatchAt`，它复用 croner，而不是另写一个表达式求值器。

研究历史是唯一的持久记录，因此运行标签记录启动方式和触发时间：`[fantasy-report:<team>:<season>:<week>:<mode>:<trigger>:<firedAt>]`。只有当时段没有运行、或只有被中断的运行且其中没有补跑时，才会启动补跑，因此每个时段最多补跑一次。已完成的报告会以记录的运行 ID 和触发时间再次交给 `cron/run-finished`；该事件要求监听器按结果 ID 和触发时间去重，Discord 发件箱通过投递回执做到这一点，因此已投递的报告不会被发送两次，而未投递的报告最终会到达其频道。运行失败、被扣留或被取消的时段已发出自己的通知，不做处理。

## 考虑过的替代方案

- **把任何没有已完成报告的时段都视为缺失** — 被否决，因为被扣留或失败的报告已发送通知，第二次运行会为该时段再发一条消息。
- **在新的 Session 事件或插件存储中记录投递** — 被否决，因为监听器必须执行的去重已使重复交接安全，而新的持久记录会为同一事实增加第二个权威来源。
- **把定时器触发规整到计划分钟，并据此推导重新投递的触发时间** — 被否决，因为一个时间表可能在同一周同一模式下触发多次，排队的运行也可能在其时段之后很久才开始，推导出的时间可能对不上监听器的去重键。
- **从 Yahoo 获取对手和开球时间** — 无法实现：匿名化的阵容、球员、联盟、记分板和比赛周抓取只带有轮空周和 `is_editable`，没有 NFL 对手或比赛开始时间，文档化的 v2 球员资源也没有赛程子资源；非官方数据源不在范围内。

## 影响

周日报告不再可能建议移动已被 Yahoo 锁定的球员，读者也能看到哪些阵容位已固定。窗口内的重启会产出错过的报告或投递已完成的报告，绝不会为同一时段重复发送。补跑只覆盖每支球队的最近时段，且只在插件启动时进行；补跑期间再次被中断的时段，以及标签中没有触发时间的已完成报告，仍只保留在研究历史中。对手和开球事实仍来自来源页面。
