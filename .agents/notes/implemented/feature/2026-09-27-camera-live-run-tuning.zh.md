# Agent Note: 首次实际运行后的摄像头截取、车辆规则、分类 Session 和门铃通知

Status: implemented

[English](2026-09-27-camera-live-run-tuning.md) | 中文

## 问题

[Ring 摄像头事件](2026-09-27-ring-camera-events.zh.md)首次实际运行暴露了四个问题。有线门铃和车库泛光灯摄像头在移动期间会再次返回同一张缓存快照；截取过程丢弃重复快照，既不报告失败，也不运行直播流回退，因此事件只带一到两帧，而不是三帧。车库判定“三辆停放的车辆，一辆轿车开着大灯怠速”触发了通知，因为车辆规则只要出现 `vehicle` 标签就会触发，而家里的车总停在车道上。分类 Session 带着主机人设和四个 schedule 工具；schedule 插件在创建后把这些工具注册到每个根 Agent 自身的作用域，`tools.restrict` 管不到那里。门铃通知要等所有画面和分类完成，约四十秒，而此时有人正站在门口。

## 决策

**重复的快照算作缺失的实时画面。** `captureFrames` 把字节与上一张相同的快照视同被拒绝或超时的快照：开启 `streamFallback` 时，该时段及之后所有时段改由现有的单次直播流补齐。未开启回退时，事件报告新的截取失败 `snapshot-stale`，因此 `captureFailure` 说明真实原因。只有连续重复可以检测；第一张快照若已是旧画面，看起来仍是新的。

**车辆按活动触发通知。** 判定新增必填的 `vehicleActivity`，取值为 `arriving`、`leaving`、`passing`、`parked`、`none` 或 `unknown`，与面向人物的 `activity` 分开，因为同一组画面可能同时出现停放的汽车和快递员。指令要求模型给出该字段，并说明车灯或运转的发动机不算移动。解析器按读取 `activity` 的方式读取它，缺失或无效时判为 `partial`，并在取值不是 `none` 时补上 `vehicle` 标签。`vehicle` 规则现在需要列出的设备，以及列在 `policy.vehicleActivities` 中的车辆活动；该字段从 `arriving`、`leaving`、`passing` 和 `parked` 中校验取值，默认 `arriving` 和 `leaving`，且不能为空。`passing` 默认关闭，因为车道外驶过的车流不是到达。历史模式把缺失的 `vehicleActivity` 默认为 `unknown`，它从不触发通知，因此该字段出现之前写入的记录在域版本 1 下仍能解析。人物规则不变。

**分类 Session 通过现有扩展点使用自己的提示词且没有工具。** 在 `agents.create` 的 setup 中，监视插件像 `dsh-persona` 行一样，用 `complete` 分类提示词遮蔽人设前缀段，调用 `suppressRuntimeContext()`，通过作用域内的 `system-prompt/assemble` 监听器返回不含工具的组装结果，并注册作用域内的 `tools.guard` 拒绝所有执行。组装监听器在所有作用域的工具提供方之后运行，因此也会去掉创建后注册到该 Agent 自身作用域的工具；守卫覆盖模型仍然点名某个工具的情况。循环把渲染后的提示词记录为该 Session 的 `system/message`，把空工具集记录在 `request/header` 中，因此模型输入仍可从日志重建。监视插件现在注入 `systemPrompt`。

**门铃按下从第一帧开始通知。** 摄像头定义新增并行的 `camera/preview`，带有事件标识和第一帧已存储画面，由提供方在截取其余画面之前发布；Ring 提供方在第一次存储后从其画面接收器发布它。`immediateDingNotice`（默认 true）、`policy.ding` 开启且配置了频道时，监视插件立即把带 `Someone rang the doorbell` 和该画面的 `camera:<id>:ding` 交给 `camera/notice`。分类后的通知保留 ID `camera:<id>`，等第一次交接结束后再发送，因此排在第二条；若已送达的第一条通知已展示过其画面，则不再附带。历史把第一条通知的结果记录为可选的 `earlyDelivery`，只要任一通知已送达，`camera` 工具就把该事件报告为已通知。移动事件仍只发一条通知。

## 考虑过的替代方案

**仍把重复快照只计一次。** 这会悄悄缩短有线摄像头的每个事件，正是观察到的问题。

**只在画面之间车辆数量变化时通知。** 数量按判定而不是按画面统计，视觉模型对部分遮挡车辆的计数也不稳定；直接询问模型车辆在做什么，只多一个它本就会推理的字段。

**把车辆移动并入 `activity`。** 人物和车辆同时出现时，判定会丢失其中一种活动。

**用 `tools.restrict({ allow: [] })` 限制工具。** 限制按设计只过滤继承来的工具，因此 schedule 工具这类 Agent 作用域工具仍然可见。

**给 `agents.create` 增加 `tools: 'none'` 选项，或让 schedule 插件跳过摄像头 Session。** 前者为一个使用方改动 Agent 工厂；后者要求每个 Agent 作用域工具的拥有方了解每个无工具使用方。组装 waterfall 本来就决定最终的工具列表。

**在 setup 中装载 `dsh-persona` 行。** 它注册的是同一个段，却多一个依赖，还会带上部署后缀，而完整段本来就会抑制后缀。

**先发布完整事件，之后再发布第二个事件。** 同一 ID 的两个 `camera/event` 会破坏使用方以它为键的幂等历史和投递。

## 影响

只要直播流可用，前门和车库事件都能获得配置的画面数量；直播流在旧快照之后几秒才开始，因此这些画面的偏移更晚。`vehicleDevices` 上停放的汽车和街上驶过的车流不再触发通知；没有 `vehicleActivity` 的模型回答不会触发车辆通知，本次改动之前存储的判定读取为 `unknown`。一次分类请求约有 60 个系统提示词 token，加上指令和画面，不含工具模式。一次门铃按下产生两条消息；提供方在预览和完整事件之间停止时，第一条消息存在，但没有历史记录或后续通知。

截取测试固定了重复快照转入直播流、未开启回退时的 `snapshot-stale`，以及重复之后直播流被拒绝的情况。监视测试固定了完整系统提示词、没有运行时上下文、在 `agent/created` 时注册的 Agent 作用域工具不可见、守卫拒绝该工具、停放和驶入的车辆、两条门铃通知及其画面和结果，以及预览画面在清理中保留。`camera-watch` 会话快照固定了分类提示词附属文件、无工具的请求头以及两条已送达的通知。
